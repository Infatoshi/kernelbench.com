I need you to write a fast MoE expert-parallel dispatch and combine for a 4xH100 SXM node (NVLink4, ~900 GB/s/GPU bidirectional, fully connected via NVSwitch). This runs across all 4 GPUs under torchrun. The reference is in reference.py and your kernel goes in solution.py. Make whatever mess you want in this directory — scratch kernels, build artifacts, nsys traces — but the final answer must be in solution.py with the same Model, get_inputs, and get_init_inputs interface as reference.py, and it must work when launched on world_size=4.

The setup: each rank owns one expert and holds `tokens` tokens of width `hidden` in bf16, plus a per-token destination index saying which expert that token was routed to. The destinations come from the gate and are UNBALANCED and different every call — one expert might get 40% of the tokens and another 15%. You must route each token to the rank owning its expert, run the expert on the received batch, route the results back, and return this rank's tokens' results in this rank's original token order, bf16. Your Model must expose the expert weight as a parameter named `expert_w` with shape (hidden,) and dtype bfloat16; the harness copies the reference's weights in with strict state_dict loading, so name and shape have to match.

Read reference.py for the exact semantics. Three things in it are load-bearing and you should understand them before writing code:

The expert's received batch has a canonical order: sorted by (source rank, source token index). The expert output for a received token is the average of that token and the PREVIOUS token in that canonical order, scaled by the expert's weight vector, with the batch treated as a ring so the first token pairs with the last. That neighbour is some other rank's token, full width — it exists nowhere on the origin rank. There is no local shortcut that reproduces this output; the tokens genuinely have to arrive, and they have to arrive in the right order.

The dispatch leg is fp8. The reference quantizes each token to e4m3 with its own per-token scale before routing, so the values that cross the fabric are fp8 values and the tolerance is tight enough that shipping bf16 instead will fail correctness. Quantization is deterministic given the input, so if you do the same thing you match the oracle exactly. Ship one byte per element plus the per-token scale. The combine leg is bf16.

The counts are data-dependent, so you have to exchange the routing metadata before you can size any receive buffer, and that round trip is on the critical path — at the small shape it IS the critical path. How you overlap or avoid it is part of the problem.

You are graded on geomean speedup against a frozen baseline: sort by destination, exchange counts, NCCL all_to_all_single with variable splits for the fp8 payload, expert, all_to_all_single back, unpermute. The baseline does the same quantization you do, so the win has to come from the kernel. Note where a good kernel finds its time: fusing the permutation into the transfer instead of materializing a sorted copy first, warp- or block-granular puts straight into peer buffers instead of one monolithic exchange, starting the combine for early-arriving tokens before the whole dispatch has landed, and not paying a full round trip for metadata.

Local permutation and quantization may use anything you like. The two all-to-alls may NOT use a c10d collective, and neither may the count exchange: no dist.all_to_all_single, no dist.all_gather, no functional collectives. Move the bytes yourself with fine-grained NVLink primitives — CUDA symmetric memory (torch symmetric memory / multimem), NVSHMEM, or p2p copies you schedule yourself. That restriction covers every file your solution imports, not just solution.py — a helper module you write is part of the solution, and sota.py may not be imported. DeepEP is the obvious prior art for this exact kernel; look it up yourself rather than guessing at the design.

Correctness tolerance on the bf16 output is 2.5e-2 rel (abs term scaled to the output rms), checked across every shape, 5 rank-distinct trials, and numeric-stress rescales. The shapes you must handle: tokens=2048 hidden=4096 (prefill-sized), tokens=8192 hidden=4096 (large batch, permutation and metadata amortize), tokens=128 hidden=4096 (decode-sized, latency-bound — the metadata round trip dominates), and tokens=2048 hidden=4095 (off-alignment hidden). Handle the case where an expert receives zero tokens.

Your flywheel: implement, profile (nsys for transfer/compute overlap and to see how much of the time is the count exchange, ncu for the permutation kernels), time it with benchmark.py, verify with `python check.py`, then iterate. Don't substitute your own correctness snippet for check.py — it runs all shapes across all ranks with distinct inputs and unbalanced routing; your spot check won't. If check.py hasn't printed PASS, you're not done. Take as long as you need to actually push the number up.
