I need you to write a fast tensor-parallel GEMM + all-reduce for a 4xH100 SXM node (NVLink4, ~900 GB/s/GPU bidirectional, fully connected via NVSwitch). This runs across all 4 GPUs under torchrun. The reference is in reference.py and your kernel goes in solution.py. Make whatever mess you want in this directory — scratch kernels, build artifacts, nsys traces — but the final answer must be in solution.py with the same Model, get_inputs, and get_init_inputs interface as reference.py, and it must work when launched on world_size=4.

The op: this is the down-projection of a tensor-parallel MLP. The full (world*k_local, hidden) weight is sharded along K, so each rank holds its own (k_local, hidden) bf16 shard and its own (tokens, k_local) bf16 activation shard. Each rank computes a partial product x @ W, those partials are summed across all 4 ranks, and then this rank's (tokens, hidden) bf16 residual is added. Read reference.py — it defines exactly this. Your Model must expose the weight as a parameter named `weight` with shape (k_local, hidden) and dtype bfloat16; the harness copies the reference's weights into your module with strict state_dict loading, so the name and shape have to match.

Two things about the data. Every rank's inputs are DIFFERENT (the harness seeds each rank distinctly), and the weight shards are different too (seeded from the rank), so sum_r(x_r @ W_r) is not (sum_r x_r) @ W — you cannot all-reduce the small activation first and do one GEMM. The reduction has to happen on the (tokens, hidden) product.

You are graded on geomean speedup against a frozen baseline: cuBLAS bf16 GEMM followed by a NCCL all-reduce, run sequentially. Beating it means overlapping. The GEMM produces its output tile by tile, and nothing stops you from moving a tile to your peers while the MMA pipeline is still working on the next one — a sequential implementation pays gemm_ms + comm_ms, a well-fused one pays about max(gemm_ms, comm_ms). The shapes are chosen so those two terms are within about 1.5x of each other, so this is worth real time.

Local compute may use any library you like — cuBLAS, CUTLASS, torch.matmul, Triton, a hand-written kernel. The cross-GPU sum may NOT: do not use torch.distributed.all_reduce, dist.all_reduce, the c10d functional collectives, or any other NCCL collective. Implement the cross-rank reduction yourself with fine-grained NVLink primitives. That restriction covers every file your solution imports, not just solution.py — a helper module you write is part of the solution, and sota.py may not be imported. Look into CUDA symmetric memory (torch symmetric memory / multimem), NVSHMEM, CUTLASS's distributed GEMM, or a producer-consumer scheme where the GEMM epilogue signals per-tile readiness to peers. Investigate the headers and docs yourself.

Correctness tolerance on the bf16 output is 2.5e-2 rel (abs term scaled to the output rms), checked across every shape, 5 rank-distinct trials, and numeric-stress rescales. The shapes you must handle: tokens=4096 k_local=2048 hidden=8192 (balanced — comm and compute are about the same length), tokens=4096 k_local=8192 hidden=8192 (compute-heavy — a good overlap should hide the comm entirely), tokens=512 k_local=2048 hidden=8192 (small, latency-bound comm with too little GEMM to hide it), and tokens=4096 k_local=2048 hidden=8191 (off-alignment hidden, forces a non-power-of-two epilogue width).

Your flywheel: implement, profile (nsys to see whether the comm is actually running concurrently with the MMA kernels, ncu for the GEMM itself), time it with benchmark.py, verify with `python check.py`, then iterate. Don't substitute your own correctness snippet for check.py — it runs all shapes across all ranks with distinct inputs; your spot check won't. If check.py hasn't printed PASS, you're not done. Take as long as you need to actually push the number up.
